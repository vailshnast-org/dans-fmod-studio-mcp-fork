# Changelog

All notable changes to this project will be documented in this file.

## [0.5.0] - 2026-10-20

> **Verification status.** Everything in this release was run against a
> live FMOD Studio 2.03.15 instance with a real game project open:
> `tests/test_live_fmod.py` (33 tests, 3 of them opt-in because they restart
> Studio, rebuild committed banks, or need a disposable project copy) covers
> every tool added here. The full suite is 174 tests: 170 run by default, and
> the 3 opt-in live tests plus 1 POSIX-only test are skipped unless enabled.
> All of them pass. Schemas the tools depend on (relationship
> and property names the manual doesn't document) were read off the live
> project before the tools were written. Where the 2.03 manual and the
> running Studio disagree, the code follows Studio and says so in a comment.

### Added — unattended automation

- **Studio control** (`studio_tools.py`, new module, runs on the MCP host so it works with Studio closed):
  - `studio_status`: install, process, Script Server, open project, unsaved changes, preference.
  - `studio_launch`: starts Studio on `FMOD_STUDIO_PROJECT`, turns on the "Enable Script Server" preference (`scriptServerEnabled` in Studio's settings file, only while Studio is closed), and waits until the server answers with that project open. It refuses if a different project is open.
  - `studio_quit`: saves, then exits. It refuses to quit with unsaved changes when `save=false`, because the save dialog would block an unattended session.
- **Headless builds** through `fmodstudiocl`: `headless_build` (exit code, warning/error lines, every bank/GUIDs file written) and `headless_validate` (FMOD's own diagnostic). Both refuse a project that Studio has open. Verified on a copy of a real project: a build writes only `Build/`, and a failure is exit code 1 with a parseable `... Error:` line.
- `project_build` now returns a build report: banks written with their sizes, plus warning/error lines from Studio's log during the build.
- **Audio analysis** (`analysis_tools.py`, new module):
  - `audio_analyze` reports peak/RMS dBFS, clipped samples, DC offset, leading/trailing silence and, with ffmpeg, EBU R128 integrated LUFS, LRA and true peak. Each file gets `flags`, and a loudness-spread warning covers variations of one sound.
  - `event_audio_report` measures every file an event plays.
  - There's no live metering to use instead: Studio's LoudnessMeter effect exposes only its settings to scripts.
  - Short one-shots (under 400 ms) report LUFS as unavailable rather than the -70 LUFS gate value.
- **Event macros**: `event_set_settings` and `event_get_settings` cover max instances, voice stealing, priority, cooldown, persistence, 3D distances and doppler.
- **Static check**: `event_lint` asks "will it make sound?" (no audio, zero length, empty playlist, -80 dB, a sustain point without loop+async, no bank, ...). `utility_validate` also lists events still called "New Event"/"Nested Event".
- **Compression**: `encoding_get`, `encoding_set` (platform default, or per-asset/per-folder overrides, plus streaming) and `encoding_clear`. Format and sample-rate-mode values were identified by building banks and reading the codec id and sample rates from their FSB5 headers: 0 PCM, 1 FADPCM, 2 XMA, 3 Vorbis, 4 AT9, 5 Opus; rate modes 0 fixed, 1 optimize, 2 preserve.
- `sound_add_nested_event`, `marker_add_tempo`, and `tag_add`/`tag_remove`/`tag_list`.
- **Team setup**: `fmod-studio-mcp --doctor` (or `--doctor --json`) checks a machine without starting the server. It covers Studio and `fmodstudiocl` (with version), the project path and its format version against Studio's (it warns before a newer Studio would upgrade a shared project), the Script Server preference and reachability, and ffmpeg. It exits non-zero on a hard failure. `--version` prints the package version. `FMOD_STUDIO_PROJECT` may be relative (e.g. `FMODProject/game.fspro`), resolved against `CLAUDE_PROJECT_DIR`, then the working directory and its parents, so one committed config works on every machine. The console script now starts at `fmod_mcp.cli`, which handles these flags before the server is built.
- `sound_add_to_track(audio=...)` assigns a file and sizes the region to it. `sound_set_properties` gains `is_async`, `start` and `length`.

### Fixed — reported in a game project's FMOD pipeline notes

- `mixer_group_route` with an event as the target reported success and changed nothing. Assigning `event.output` only created an unused JS field. Events now route through their `MixerInput`, verified by read-back.
- `sound_add_to_track` accepted `length: 0`, which produced a silent instrument that couldn't be resized. A length of 0 is now rejected (pass `audio=` to size to the file), and `sound_set_properties(length=...)` can resize.
- `sound_set_owner` onto a Scatterer was silently ignored. A Scatterer's playlist is its inner MultiSound (`scatterer.sound`), which is what is now used.

### Added

- **Validated property and relationship editing** — `utility_set_properties`, `utility_get_properties`, `utility_set_relationship`, `utility_describe_entity`. Before this, `utility_dump` could *read* every plain property (instrument `looping`/`volume`/`pitch`, effect parameters such as reverb decay or compressor threshold, modulator depth) but nothing could *write* one. That made most of Studio's deck unreachable. Names are checked against the object's `ManagedPropertyMap`, so a misspelled name errors instead of creating a JS field FMOD ignores. Value types must match, values are read back, and Studio-clamped values are reported. Values are scalars only, and names must be plain identifiers.
- **Modulators** (`modulator_tools.py`, new module): `modulator_add` (Randomizer / ADSR / Sidechain / Autopitch, the four types `addModulator` documents) with optional initial settings, and `modulator_list`. Random pitch/volume variation on repeated sounds wasn't possible before.
- **Parameter-driven design**: `parameter_add_global` (project-level parameters via `workspace.addGameParameter`), `parameter_set_cursor` (set a parameter value while auditioning, so you can actually hear layering/transitions react), `parameter_add_condition` (`Triggerable.addParameterCondition` on instruments, loop regions, transition markers and regions, with range or label), and `sound_add_to_track(parameter=...)` to place instruments on a parameter sheet instead of only the timeline. `parameter_add` now accepts all 11 documented `parameterType`s (adds `UserDiscrete`, `Speed`, `SpeedAbsolute`, `DistanceNormalized`), takes `labels` at creation, and rejects `min >= max`.
- **Undo/redo**: `project_undo`/`project_redo` through `studio.window.triggerAction(actions.Undo/Redo)`. The docs and injected instructions previously said there was no undo from the terminal. Also `project_trigger_action` for a small allowlist of non-destructive menu actions (`RefreshModifiedAssets`, `ValidateProject`, `ExportGuids`, ...), plus `project_export_guids`, `project_list_plugins` and `project_get_version`.
- **Building and auditing events**: `event_create_from_audio` imports files and builds a complete playable event (SingleSound, or a MultiSound playlist for several files) with optional folder/bank/spatializer/looping in one call. If a step fails it deletes the half-built event. Also `event_describe` (tracks, instruments, parameters, markers and banks in one call), `event_list_sounds`, `audio_import_batch`, `sound_set_properties`, `sound_set_fade` (`setFadeInCurve`/`setFadeOutCurve`), and `event_set_3d_attributes` for auditioning distance/panning. `event_create` takes `spatializer` (2D/3D via `workspace.addEvent`). `event_info` now reports `is3D`, `isOneShot` and banks.
- **Mixer**: `mixer_return_create` and `mixer_send_add` for project-level return buses shared across events (before, only per-event returns existed), `mixer_effect_remove`, and `mixer_effect_add(settings=...)`.
- **Automation on any property**: `automation_add_curve`/`automation_add` accept any automatable property (an effect's cutoff, wet level, ...), not just `volume`/`pitch`/`gain`. Names outside those three are checked to exist on the live target first.
- `utility_list` accepts any model entity name, with `include_derived` and `within` (search inside one object). `utility_dump` now also lists each relationship's first destinations (guid, name, entity).
- `tests/test_tools_registration.py`: every generated command is now parsed by Node.js (parse only, nothing runs), and command bodies are checked for ES6-only syntax that Studio's older JS engine may reject. This catches statement-level syntax errors like the 0.4.0 `a;,b;` `automation_add_curve` bug, which the old bracket check couldn't see (confirmed by reintroducing that bug). Skipped when `node` isn't installed. The bracket check also understands single-quoted JS strings now.
- `docs/fmod-api/`: local copy of the FMOD Studio 2.03 scripting API reference (raw HTML plus a greppable Markdown conversion).

- **Snapshot authoring**: `snapshot_set_property` (capture a value such as a group's volume or an effect parameter, creating or updating a `SnapshotProperty`, with the strip scoped automatically), `snapshot_list_properties`, `snapshot_remove_property`, and `snapshot_set_settings` (intensity, behavior).
- **Playlists**: `multi_list_entries`, `multi_add_entry`, `multi_remove_entry`, `multi_set_weight` (creates the per-entry `PlayPercentage` Studio needs), and `multi_set_playlist`.
- **Plug-ins**: `mixer_effect_add_plugin` and `sound_add_plugin` (through `workspace.createPlugin`). Both check the name against `findAvailablePlugins()`, and error if you pass an effect where an instrument is needed or the other way round.
- **Assets** (`asset_tools.py`, new module): `audio_asset_info` and `audio_asset_move` (`setAssetPath`, which moves the file on disk; validated relative path, same extension, no overwrite). `audio_assets` takes `folder` and `unused_only` and reports length, channels, sample rate and how many instruments use each asset.
- **Automation editing**: `automation_set_point` (position, value, curve shape, S-curve), `automation_remove_point`, `automation_delete_curve`, and `automation_show_track` (shows the automation lane in Studio's editor). `automation_list` now includes `pointDetails` (point guids and shapes).
- **Bank folders**: `bank_create(folder=...)`, `bank_set_folder`, and `folder_create(kind="BankFolder")`.
- **VCAs**: `vca_unassign` and `vca_list_strips`.
- Live tests for every new tool. An autouse fixture stops `ensure_backup` from saving the open project during tests. Tests also delete the `ParameterPreset`s and plug-in `DataFile`s that outlive the objects that created them. A GUID-export test restores the project folder byte-for-byte afterwards.

### Fixed

- **`audio_assets` always returned an empty list.** It queried the abstract `model.Asset` type without `includeDerivedTypes`, which returns nothing on 2.03.15 (0 results against 97 real audio files). It now lists `AudioFile`s.
- **Every tool reported audio assets with `name: null`** (`audio_import`, `sound_info`, `sound_set_audio_file`, ...). An `AudioFile` has neither `.name` nor `getPath()`; its identity is `assetPath`. The shared `N()`/`P()` helpers now fall back to `assetPath` and `asset:/<assetPath>`, which is a valid lookup path.
- **`vca_assign` failed on every call.** It tried relationships named `vcas`/`assignedVCAs`, which don't exist. The real one is the strip's `masters` (on the VCA side: `slaves`).
- **`snapshot_bind_group` never bound anything.** It used `snapshot.relationships.groups`, which doesn't exist, and returned `bound: false` every time. It now scopes the strip through a real `SnapshotTrack`.
- **Some native Studio errors showed up only as "Invalid JSON response from FMOD Studio: None".** Errors such as a relationship destination of the wrong entity type abort the entire script instead of throwing a catchable JS exception, so the wrapper's `catch` never ran. `parse_response` now finds the `error(): ...` line Studio prints and reports that message.
- `parameter_add_global` created a *local* parameter (`isGlobal: false`), because `workspace.addGameParameter()` alone doesn't make a parameter global. It now sets `isGlobal` and reads it back.
- `parameter_add_condition`: the documented two-argument form (no `max`) throws on 2.03.15, and a label string is accepted but silently stored as index 0. It now always passes three arguments and resolves labels to their index through `enumerationLabels`.
- `sound_add_to_track(parameter=...)` aborted with "expects a destination of entity type 'Parameter'". A parameter sheet is the event's `ParameterProxy`, not the `GameParameter`. A new `__sheet()` helper finds it, or adds one for a global parameter.
- `mixer_send_create` looked for `returnTrack.mixerGroup`. A `ReturnTrack`'s bus is its `mixerReturn` (an `EventMixerReturn`). `automation_show_track` had the same assumption.
- `audio_asset_move`: `setAssetPath()` returns `undefined` on 2.03.15 even when the move succeeds, so success is judged by reading the path back.
- The live automation test left a `ParameterPreset` behind on every run. Deleting an event doesn't delete the presets its parameters created.

- **`utility_validate` never validated anything.** It called `studio.project.validate()`, which isn't part of FMOD's scripting API. The resulting throw was caught and returned as a meaningless string. It now runs a real audit: events in no bank (these never ship), events with no instruments, SingleSounds with no audio (these play silence), and invalid objects.
- **`mixer_send_create` relied on `addEffect('SendEffect')`, which isn't among the documented `addEffect` types** (the entity is `MixerSend`). It also set `fx.target` without checking that the link took. Sends now fall back to creating a `MixerSend` and appending it to the chain. They try candidate return-relationship names and keep the first one that actually lists the return as a destination; otherwise they remove the half-made send and raise.
- `mixer_group_create`'s docstring promised "routed to Master by default", but nothing set the output. It now routes to the master bus explicitly when no `output_target` is given.

- **`marker_add_transition_timeline`** — FMOD's real "Add Transition Timeline" feature (crossfaded seamless transitions instead of a hard jump-cut), previously unavailable. Investigated live: `TransitionSourceSound`/`TransitionDestinationSound` require both `audioTrack` and `parameter` (set to a `TransitionTimeline`) relationships to be valid — confirmed by creating one without them and observing `isValid: false`, both in a fresh throwaway object and in objects already sitting in a real project, which is what those mystery objects flagged earlier this session actually turned out to be (a genuinely incomplete/invalid attempt at this feature, not random debris). The tool creates the `TransitionTimeline` and a correctly-bound source/destination pair overlapped by `crossfade_length` seconds. Structural validity is verified live in a regression test; the actual audible crossfade quality hasn't been verified against a real render and should be auditioned in Studio.

## [0.4.0] - 2026-08-21

### Fixed

- **Critical: `automation_add_curve` failed for its core use case — any call with 2 or more points.** Its multi-point JS body joined semicolon-terminated statements (`"...addAutomationPoint(...);"`) with a comma separator, producing `stmt1;,stmt2;,stmt3;` — a bare comma at statement position, a JS syntax error. A parse-time error like this is caught by neither the command wrapper's own `try/catch` (which only catches runtime exceptions) nor a clean thrown-error response, so it surfaced as an opaque `"Invalid JSON response from FMOD Studio"` with no indication of what actually went wrong. This bug existed since the tool was first written; every prior "successful" test of it earlier in this project's life used hand-written JS in ad hoc test scripts, never the actual registered tool function, which is why it went undetected until called end-to-end for real. Fixed by joining with `""` instead of `","`. Added a live-FMOD regression test that creates a throwaway mixer group + parameter, calls the real tool with 3 points, and verifies the result — cleans up after itself.
- **`Automator.addAutomationCurve()` unconditionally creates a new curve on every call — it never reuses one for the same driver,** contrary to what `automation_add`'s docstring assumed ("Studio keys curves by that triple, so addAutomationCurve returns/extends the matching curve" — confirmed live, false). Every incremental `automation_add` call for the same target/property/driver therefore created a *separate* one-point curve instead of adding a point to the existing curve — four calls produced four disconnected single-point curves, not one four-point curve. All the automation *values* survived correctly (verified live on a real project: all 4 layers had exactly this fragmentation, with all originally-intended values intact across the fragments), so no data was lost, but no fragment was long enough to actually drive a crossfade. Both `automation_add` and `automation_add_curve` now look for an existing curve bound to the same driver (matched via the curve's `relationships.parameter` destination guid) before creating a new one.
- **`automation_list` was a non-functional stub that always returned `curves: null`,** regardless of what automation actually existed. This is the direct reason the fragmentation bug above went undiagnosed — the AI correctly checked "does automation exist here?", got `null` back every time, and concluded nothing had been created at all (matching the exact same failure shape as the `utility_dump`/`sound_info` incidents from the previous release: the verification tool couldn't tell the truth, so a real problem got misdiagnosed as "nothing exists" instead of "something exists but is wrong"). Rewritten to do real introspection: every curve's guid, the driver parameter guid it's bound to, and its actual sorted `[position, value]` points.

## [0.3.0] - 2026-08-21

### Fixed

- **`safe_path()`'s system-directory block was silently bypassable on macOS.** `/etc`, `/tmp`, `/var` etc. are symlinks into `/private/...` on macOS — `os.path.realpath()` resolves the input path through that symlink before the blocklist check runs, so a literal `"/etc"` prefix match against an already-resolved `"/private/etc/..."` path never fires. Caught by CI (`test_posix_system_dir_rejected` failed on `macos-latest`, passed on Linux/Windows). Fixed by resolving each blocked directory through `realpath()` too, so both sides of the comparison go through the same resolution.
- **Critical: every tool's `guid` field returned `null`, and every `path` field silently returned the object's name instead.** `fmod_mcp_shared/protocol.py`'s shared `G()`/`P()` JS helpers — injected into *every* command wrapper — read `o.guid` and `o.path`, neither of which exist on a real FMOD `ManagedObject` (confirmed live against FMOD Studio 2.03.14: the real properties are `.id` and the `getPath()` *method*). `N()`/`.name` was correct, which is why this went unnoticed — names always worked, so the server looked functional in casual use, but the GUID-chaining workflow the docs describe as central ("echo results back, chain into the next call") was broken for every single tool since 0.1.0, and `workspace_info`'s roots being null (previously misdiagnosed as a "project not open" issue) was the same bug. All 91 tools share this one wrapper, so the fix is centralized; verified live end-to-end (lookup by path → get guid → look up again by that guid → same object) against a running FMOD instance. Added `tests/test_live_fmod.py`, a regression suite that runs automatically whenever FMOD's Script Server is reachable and skips otherwise, since this class of bug is invisible to the stub-client tests every other test file uses.
- `sound_create` built its JS command body with an f-string instead of passing `sound_type` through the `p` param object like every other tool — safe today only because of an allowlist check two lines above it, but a latent injection point if that check is ever loosened. Now passed as `p.sound_type`, consistent with the rest of the codebase.
- **`event_add_track`/`event_list_tracks` returned a track's own GUID where callers actually needed its mixer group's GUID.** A `GroupTrack` and its `.mixerGroup` are different objects — only the mixer group has `addAutomator()`, so chaining a track GUID straight into `automation_add_curve`/`mixer_group_volume`/`mixer_effect_add` fails with `"target has no addAutomator()"` (or the equivalent) every time, which is what was being reported as "automation_add_curve returns a scripting error regardless of how I reference the parameter" — the parameter reference was never the problem. Both tools now return `trackGuid` and `mixerGroupGuid` separately and labeled, and the docstring says which one each downstream tool needs. Verified live: `automation_add_curve` succeeds immediately once given the mixer group GUID.
- **`event_list_tracks`/`bank_list_events` always returned an empty list even when tracks/memberships existed.** Same root-cause family as the `G()`/`P()` bug: the code read `relationship.toArray()`/`relationship.added()`, neither of which exist on a real `ManagedRelationship` — the actual property is `.destinations` (confirmed live and in FMOD's own docs). Because the empty-list result degrades gracefully instead of erroring, this silently told callers "no tracks exist yet," which is almost certainly why one live project ended up with 8 duplicate tracks (4 created, reported as absent, re-created under slightly different names). Fixed in both tools.
- **`mixer_effect_list` always returned an empty list.** Same `.toArray()/.added()` bug — the real relationship is `chain.relationships.effects.destinations` (confirmed live, and confirmed *ordered*, matching "adds to the end of the chain"). Now also tags each entry with its `entity` type, since a group's chain always contains built-in `MixerBusFader`/`MixerBusPanner` items alongside any effects actually added.
- **`folder_create`'s existing-folder lookup was silently broken the same way, risking the same duplication bug as the tracks issue above.** It walked `folder.children` (a property that doesn't exist — `undefined`, not just empty) to check whether a path segment already existed before creating it, so it *always* thought nothing existed and *always* created a new folder, even when reusing one was intended (`folder_create` documents itself as "safe to call repeatedly" — it wasn't). The real relationship is `folder.relationships.items.destinations`. Fixed and verified live: calling `folder_create` on an already-existing path now finds and returns the existing folder instead of duplicating it.
- **`folder_create(kind="AssetFolder", ...)` was silently guaranteed to fail** with a confusing `"cannot set property 'name' of null"` — `model.AssetFolder` isn't a real, instantiable entity in FMOD Studio 2.03.14 (confirmed live: `studio.project.model.AssetFolder` doesn't exist, and `project.create("AssetFolder")` returns `null`; the official scripting docs list only `model.Folder` and the `model.MasterAssetFolder` singleton, no per-folder asset-organization type). `folder_create` now checks for a `null` result from `project.create()` and raises a clear, typed error instead of crashing on the next line. `EventFolder` creation is unaffected and works correctly.
- `folder_list` was already correct — it lists via `studio.project.model.Folder.findInstances()` directly rather than walking `.children`, so it was never affected by this bug family. (Corrects an earlier note in this changelog that mistakenly flagged it as broken alongside `folder_create`.)
- **`utility_dump` — the tool whose entire job is discovering capabilities the curated tools don't expose — returned nothing.** It called FMOD's own `dump()`, which only logs to Studio's internal console window and returns `undefined` to any script; confirmed live. This is the actual root cause behind several "the MCP doesn't support X" conclusions reached during live sessions on this project (per-instrument loop mode, several relationship names): the AI correctly reached for the one tool built for exactly this situation, and got silence back — not evidence the capability didn't exist. Rewritten to do real introspection instead: every plain settable property with its current value, and every relationship with its cardinality and current destination count, both enumerated directly off a live object rather than routed through FMOD's console-only `dump()`. `00_core.md` now instructs the model to use it before concluding anything "isn't scriptable."
- **`00_core.md` (the injected system instructions) referenced tool names that don't exist**: `track_add_to_event`, `audio_add_to_track`, `effect_add`, `object_delete`, `object_is_valid`, `event_wipe_tracks`, `bank_clear` — the real names are `event_add_track`, `sound_add_to_track`, `mixer_effect_add`, `utility_delete`, `utility_is_valid`, and the last two were never built at all. Rewritten with correct names throughout, ~30% shorter.
- **Tool-list and instructions token footprint trimmed** (~9,700 → ~9,100 tokens for the 91-tool schema list; ~1,700 → ~1,200 for instructions) — both are resent every turn by the MCP protocol, so this is recurring overhead, not one-time. Trimmed the worst-offender docstrings (`automation_add_curve`, `automation_add`, `sound_add_to_track`, `utility_dump`, `mixer_send_create`, `project_build`, `folder_create`) without dropping load-bearing warnings (e.g. trackGuid vs mixerGroupGuid). For workflow-focused sessions, `FMOD_STUDIO_MCP_PROFILE` (`events`/`mixer`/`banks`/`minimal`) cuts tool *count*, a bigger lever than description trimming alone.
- **`sound_set_audio_file`/`sound_set_owner` reported success without confirming the assignment actually took.** Both now read the relationship back and raise a typed error if it didn't stick, instead of returning a bare guid that only proves the JS call didn't throw. `sound_info` now reports `hasAudioFile`/`audioFileName` explicitly. Root-caused a real incident: an AI session's audio-attachment calls actually succeeded, but its *verification* calls (`sound_info`/`utility_dump`, pre-fix) couldn't confirm that, leading it to delete a correctly-built event and rebuild an incomplete one that skipped instrument creation entirely — confirmed via the command-history archive, not guessed.
- **`parameter_list`/`parameter_set_initial`/`parameter_set_labels` could never actually find a parameter by name — a `GameParameter` has no `.name` property at all.** The real name lives on a separate `ParameterPreset` object, reachable only via `relationships.presetOwner` (confirmed live via `utility_dump`). `parameter_set_initial`'s value-set happened to work anyway by accident (its `||found` fallback landed on `initialValue`, which *is* a direct property), but the name lookup that finds `found` in the first place never matched anything — meaning these tools have been silently non-functional for their stated purpose since they were added. Fixed in all three, plus `parameter_add` now checks for an existing same-named parameter first and errors instead of creating a duplicate (found and removed one real "Intensity (2)" duplicate this exposed in a live project — the delete had to target the `ParameterPreset` via `presetOwner`, not the transient `GameParameter` proxy `getParameterPresets()` returns, which doesn't durably delete on its own).
- **`event_add_marker_track` always created a new marker track, never reused an existing one** — same silent-duplication risk as the tracks/folders bugs above. Now get-or-creates (returns `reused: true/false`).
- **`marker_add_named`/`marker_add_region` had no duplicate-name guard.** Both now error with the existing marker's guid instead of silently creating a second one with the same name.
- **`audio_import` had no way to catch a blank/silent source render.** A DAW bounce that came out empty imported "successfully," attached to an instrument "successfully," and only failed silently at playback. Added a best-effort WAV silence check (stdlib `wave`, no new dependency; skips gracefully on non-WAV/24-32-bit/compressed formats rather than risk a false positive) that rejects a file whose first 10 seconds are below ~-60dBFS peak, with a clear error pointing at the source render.

### Added

- `fmod_mcp_shared/path_safety.py`: `safe_path()` blocks path traversal and reads from system directories (`C:\Windows`, `/etc`, etc.), mirroring Reaper-MCP's guard. Applied to `audio_import`.
- `fmod_mcp/safety.py`: `ensure_backup()` — before `event_delete`, `bank_delete`, `mixer_group_delete`, `snapshot_delete`, `utility_delete`, or `marker_delete` runs, saves the project and copies its directory (excluding `Assets`/`Build`) to a timestamped sibling, once per session. Mirrors Reaper-MCP's auto-backup safety net.
- `SECURITY.md`, `.gitattributes`, `.github/dependabot.yml` for parity with the sibling Reaper-MCP/AudacityMCP repos.
- `fmod_mcp/tools/audition_tools.py` — `event_play`, `event_stop`, `event_toggle_pause`, `event_key_off`, `event_return_to_start`, `event_playback_status`. Closes a real gap: the project's own docs already told the model to "play it early and often" and "use the audition tools" — no tool actually did that until now.
- `fmod_mcp/tools/marker_tools.py` — full marker-track support: `event_add_marker_track`, `marker_add_named`, `marker_add_region`, `marker_add_sustain_point`, `marker_add_transition`, `marker_add_transition_region`, `marker_list`, `marker_rename`, `marker_set_position`, `marker_set_region`, `marker_delete`. Powers loop-region/transition-driven interactive music, not just parameter-driven crossfades.
- `mixer_tools.py`: `vca_create`/`vca_list`/`vca_info`/`vca_volume`/`vca_assign`, and `mixer_send_create` (per-event return track + send, e.g. a shared reverb bus). `SendEffect` added to `ALLOWED_EFFECTS`.
- `project_build` now accepts optional `banks`/`platforms` to scope a build instead of always rebuilding everything.

### Fixed (continued)

- `constants.py`'s `ALLOWED_CREATE_TYPES` and `utility_tools.py`'s `ALLOWED_LIST_TYPES` listed `"VCA"`/`"Bus"` as entity names — FMOD's real scripting entity names are `MixerVCA`/`MixerBus`, so `vca_create`-equivalent calls and `utility_list("VCA")` would have failed against a real FMOD Script Server the moment they were used. Corrected both.

## [0.2.0] - 2026-08-20

### Added

- **Interactive / evolving music support** — parameter-driven mixer automation is FMOD's standard technique for scores that react to gameplay (layered tracks crossfaded by a game parameter as the player moves through the world).
- `automation_tools.py`: `automation_add_curve` (bind `volume`/`pitch`/`gain` to a game parameter or an event timeline, with an arbitrary set of points), `automation_add` (append one point), `automation_list`.
- `snapshot_tools.py`: `snapshot_create`, `snapshot_list`, `snapshot_info`, `snapshot_rename`, `snapshot_delete`, `snapshot_bind_group` — mixer state presets the game activates as blendable layers.
- New `MAX_AUTOMATION_POINTS` safety cap (100) in `fmod_mcp_shared/constants.py`.
- `automation_tools` added to the `events` profile; `automation_tools` + `snapshot_tools` added to the `mixer` profile; both included in `full`.
- The existing `sound_create` / `sound_set_owner` / `sound_set_audio_file` trio already assembles Multi-instrument layering playlists (each SingleSound nestling into a MultiSound), so layering tracks are fully automatable end-to-end.

## [0.1.0] - 2026-08-20

### Added

- Initial release. MCP server for FMOD Studio authoring via the built-in JS scripting terminal (TCP 3663).
- 50+ curated tools across 9 modules: Project, Events, Sounds, Parameters, Banks, Mixer, Folders, Workspace, Utility.
- Typed, self-trapping JS command wrapper (`format_command`) with inert JSON param injection and safety validation (names, dB ranges, type/lists whitelists, audio-file paths/formats).
- Read-until-idle TCP bridge with typed connection/timeout errors, cross-process file mutex, and a 30-day command-history audit trail.
- Profile-trimmable tool surface (`FMOD_STUDIO_MCP_PROFILE`: `full`, `events`, `mixer`, `banks`, `minimal`).
- UTF-8 stdio fix and parent-liveness watchdog inherited from ReaperMCP's proven client lifecycle.
- Instructions injected into the MCP server (`fmod_mcp/instructions/00_core.md`).
- Test suite: protocol, client framing, registry, limits, and an end-to-end harness that exercises every registered tool.
